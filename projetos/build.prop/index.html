Pixel Prop Builder

Acervo navegável e atualizado automaticamente do build.prop completo de cada Pixel, direto das imagens OTA oficiais do Google.

Shell Auto-atualizado GPL-3.0-or-later Android · Pixel GitHub Actions
Ver no GitHub Releases

O que faz

Mantém um acervo versionado do build.prop completo de cada Pixel, extraído diretamente das imagens OTA oficiais do Google e atualizado sozinho. O .prop de cada aparelho fica guardado no repositório e publicado como asset de release, pronto para navegar ou baixar sem precisar de ferramenta nenhuma.

Cada arquivo é o conjunto completo e organizado das propriedades de build daquele aparelho e build exatos: product, vendor, odm, system, system_ext, system_dlkm e mais.

Obtenha um .prop

Duas maneiras, sem configuração:

  • Navegue pelo repositório: abra a pasta do aparelho <codename>/ e escolha <codename>_<build_id>.prop.
  • Baixe pelas Releases: pegue o arquivo na release mais recente, com a tag build-YYYYMMDD.

O acervo cobre 25 aparelhos (codenames como akita, husky, komodo, caiman, comet, lynx).

Exemplo

bash 
$ ./download_latest_ota_build.sh akita
$ ./extract_images.sh
  →  akita/akita_16596456.prop

$ ls akita/
akita_16271449.prop   akita_16451184.prop   akita_16484274.prop
akita_16521119.prop   akita_16594701.prop   akita_16596456.prop

$ head akita/akita_16596456.prop

Compile você mesmo

Para extrair um .prop localmente em vez de baixá-lo, precisa de um ambiente Unix-like (Linux ou macOS com Bash) e das dependências que o requirements.sh instala na maioria dos gerenciadores de pacotes (apt, pacman, dnf, yum, zypper, apk, xbps, brew, Termux): p7zip, e2fsprogs, erofs-utils, lz4, cpio, dos2unix, aria2, curl, xxd, jq e Python 3.8+ com payload_dumper. 

git clone --recurse-submodules https://github.com/VictorGabriel7Dev/build.prop
cd build.prop
./requirements.sh
./download_latest_ota_build.sh <device> [device ...]   # ex.: husky  |  cubs grizzly_beta
./extract_images.sh                                    # -> <codename>/<codename>_<build_id>.prop
A extração lê cada partição do payload uma de cada vez (baixo consumo de memória) e lida com imagens EROFS, ext4, sparse e boot/init_boot. Os aparelhos suportados são as imagens de fábrica e OTA das páginas oficiais do Google (incluindo as de OTA Beta).

Automação

Um pipeline do GitHub Actions (.github/workflows/build.yml) mantém o acervo atualizado sem intervenção:

  • Roda semanalmente, e sob demanda via workflow_dispatch com uma lista de aparelhos separada por espaços ou all; cada aparelho compila em paralelo.
  • Extrai o .prop, faz commit dos novos em <codename>/ e os publica como assets sob uma única tag diária (build-YYYYMMDD).
  • Pula os .prop já publicados e notifica o Telegram com links de download.
Forks que rodam o pipeline precisam de dois secrets: TELEGRAM_BOT_TOKEN (do @BotFather) e TELEGRAM_CHAT_ID.
