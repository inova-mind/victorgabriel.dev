Pixel Prop Builder

Acervo navegável e atualizado automaticamente do build.prop completo de cada Pixel, direto das imagens oficiais do Google.

Shell Auto-atualizado GPL-3.0-or-later Android · Pixel stable · beta · canary
Ver no GitHub Releases

O que faz

Mantém um acervo versionado dos 4 últimos builds de cada canal (stable, beta e canary) de cada Pixel recente, extraído diretamente das imagens oficiais de fábrica e OTA do Google e atualizado sozinho.

Cada entrada é o build.prop completo, mesclado de todas as partições (system, system_ext, product, vendor, odm e as imagens _dlkm), e traz o ro.boot.vbmeta.digest (o hash do verified boot). Tudo fica guardado no repositório, indexado num index.json legível por máquina e publicado como asset de release. Nenhuma ferramenta necessária.

O que há dentro

  • Todo Pixel recente (Pixel 6 e mais novos), 25 aparelhos.
  • Três canais por aparelho: stable, beta e canary, os builds mais recentes de cada (sujeito ao que o Google realmente publica; alguns aparelhos recém-lançados ainda têm só um ou dois builds no canary).
  • build.prop completo por build (cerca de 300 a 390 propriedades), mesclado de todas as partições.
  • vbmeta.digest (o hash do verified boot) guardado junto das propriedades.

Obtenha os dados

Três maneiras, sem configuração:

  • Navegue pelo repositório: abra a pasta do aparelho <codename>/ e escolha um arquivo. A nomenclatura diz o canal: <codename>_<incremental>.prop (stable), <codename>_beta_<incremental>.prop e <codename>_canary_<incremental>.prop.
  • index.json: um manifesto legível por máquina que mapeia cada aparelho para canal para build mais recente, com model, soc, first_api_level, security_patch, android, build, incremental e vbmeta_digest. Ideal para automação.
  • Releases: baixe todo o acervo como um único .zip (mais o index.json) na release mais recente, com a tag build-YYYYMMDD.

Exemplo

bash 
$ ls akita/
akita_16271449.prop          # stable
akita_beta_16708287.prop     # beta
akita_canary_16484274.prop   # canary
...

$ jq -r '.devices.akita.model' index.json

Compile você mesmo

Para extrair um único .prop localmente em vez de baixá-lo, precisa de um ambiente Unix-like (Linux ou macOS com Bash) e das dependências que o requirements.sh instala na maioria dos gerenciadores de pacotes (apt, pacman, dnf, yum, zypper, apk, xbps, brew, Termux): p7zip, e2fsprogs, erofs-utils, lz4, cpio, dos2unix, aria2, curl, xxd, jq e Python 3.8+ com payload_dumper. 

git clone --recurse-submodules https://github.com/VictorGabriel7Dev/build.prop
cd build.prop
./requirements.sh
./download_latest_ota_build.sh <device> [device ...]   # ex.: husky  |  cubs grizzly_beta
./extract_images.sh                                    # -> <codename>/<codename>_<build_id>.prop
A extração lê cada partição do payload uma de cada vez (baixo consumo de memória) e lida com imagens EROFS, ext4, sparse e boot/init_boot. Os aparelhos suportados são as imagens de fábrica e OTA das páginas oficiais do Google (incluindo as de OTA Beta).

Automação

O acervo se mantém atualizado sozinho: conforme o Google publica novos builds, eles são extraídos (completos, todas as partições, com vbmeta.digest), os novos .prop entram em <codename>/, o index.json é atualizado e uma release datada (build-YYYYMMDD) é criada para notificar quem acompanha a cada leva.

Um .github/workflows/build.yml genérico e sob demanda (workflow_dispatch) fica disponível como alternativa manual para compilar o .prop mais recente de um aparelho.
